# 10. Orin2 Ubuntu 22.04 초기 설정과 Ouster 연결

## 한 줄 요약
재설치한 Orin2에서 USB Wi-Fi 드라이버, 네트워크 설정, ROS2 Humble, Ouster 드라이버를 순서대로 다시 올렸다. 하루 안에 Wi-Fi 드라이버 충돌, GPU 드라이버 사고(검은 화면), OpenCV 패키지 누락, Ouster 펌웨어와 드라이버 호환 문제가 연달아 나왔고 대부분 해결했다. 계획했던 `unitree_ros2` 설치와 `/sportmodestate` 수신은 이 세션에서 시작하지 못했다.

## 1. USB Wi-Fi 어댑터 드라이버
- 어댑터: TP-Link T4U Plus, USB ID `2357:0115`, 칩셋 RTL88x2bu. `rtl88x2bu` DKMS는 커널 `5.15.185-tegra`용으로 이미 `installed` 상태였는데 모듈이 로드되지 않았다.
- 증상: `modprobe`가 `cfg80211_*` 심볼이 `disagrees about version`, `Unknown symbol`로 실패. `vermagic`은 일치해서 커널 버전 문제가 아니었다.
- 원인: `lsmod`에서 `cfg80211`이 `compat` 모듈에 의존해 로드돼 있었다. 즉 커널 내장 cfg80211이 아니라 백포트 버전(Intel Wi-Fi 지원용)이 `/lib/modules/5.15.185-tegra/updates/compat/`에 깔려 있었고, `updates/` 디렉토리는 기본 모듈 경로보다 우선한다. `88x2bu`는 내장 cfg80211 기준으로 빌드돼서 심볼 체크섬이 안 맞았다. 이 Orin2에는 M.2 Wi-Fi 카드가 없어서(`lspci`에 아무것도 안 나옴) 백포트가 필요 없었다.
- 사고: `updates/` 폴더 전체를 `.bak`로 옮기고 재부팅했더니 부팅 화면 뒤 검은 화면. SSH로는 접속됐고 `journalctl`에 `Failed to insert module 'nvgpu': Invalid argument`. `nvgpu`(Tegra GPU 드라이버)가 같은 `updates/` 안에 있었기 때문이다. 폴더를 원위치하고 `depmod -a` 후 재부팅해서 복구했다.
- 정밀 처리: `updates/compat`, `updates/net/wireless`, `updates/net/mac80211` 3개만 `~/wifi_backport_disabled/`로 옮기고 `depmod -a`. 재부팅 전에 `find ... -maxdepth 2`로 `nvgpu.ko`, `opensrc-disp/`, `dkms/88x2bu.ko` 등이 남아 있는지 확인하고 갔다. 이후 드라이버가 정상 로드됐다.
- 교훈: 모듈 디렉토리는 통째로 옮기지 않는다. 옮기기 전에 안에 무엇이 있는지 보고, 재부팅 전에 검증한다. 이 문제는 나중에(43번 세션) 같은 패키지(`backport-iwlwifi-dkms`)가 다시 문제의 중심이 된다.

## 2. Wi-Fi 설정 재적용 (07번 세션의 설정 1~6)
- 자동연결과 우선순위, 파워세이브 끄기, MAC 랜덤화 끄기, `wifi-reconnect.service`, `wifi-watchdog.sh`(cron 1분), `ping-logger`를 다시 만들었다. 파일은 전부 `sudo bash -c 'cat > ... << "EOF"'` 방식으로 써서 편집기 줄 깨짐을 피했고, `ping-logger.sh`에는 처음부터 `LC_ALL=C`를 넣었다.
- 인터페이스 이름이 Orin Nano 때와 다르다: 무선은 MAC 기반 이름(`wlx<MAC>`, USB 동글이라 `wlan0`가 아님), 온보드 유선은 `eth1`이 아니라 `enP8p1s0`.
- 로봇 내부망용 유선 프로파일은 정적 `192.168.123.20/24`로 설정. 도크(Orin1)를 켠 뒤 `ping`으로 Go2(`.161`)와 Orin1(`.18`)이 손실 0%, 왕복 1ms 미만으로 확인됐다.
- `Wired connection 2`는 중복 프로파일이 아니라 별개의 실제 프로파일이었다(삭제 전에 `nmcli connection show "<이름>"`으로 내용을 확인해서 삭제를 피함).

## 3. ROS2 배포판: Humble
- 사용자가 처음부터 Humble을 쓸 생각이었고, Unitree ROS2가 공식적으로 Humble을 지원하는지 조사. Claude는 Ouster를 Orin2에 직결해 새로 파이프라인을 만드는 구조라면 Humble로 가도 문제가 적다고 정리했다.
- 설치 중 `add-apt-repository universe` 확인 프롬프트에 Enter만 누르면 된다는 안내, 오래전에 등록된 Claude Desktop apt 저장소가 서명 키 없이 방치돼 경고가 나는 문제도 있었다(ROS2와 무관).

## 4. Ouster 연결 구조: Orin1을 거치지 않고 Orin2에 직결
- 05번 세션에서는 Ouster가 어디에도 안 보였다. 이번에 확인된 사실은 Ouster가 Orin2의 USB 이더넷 어댑터(AX88179, 인터페이스 `enx<MAC>`)에 직접 연결돼 있고, Orin1을 거치지 않는다는 것이다.
- 확인 방법: `avahi-browse`로 해당 인터페이스에서 mDNS를 확인하고, `ping6 -I <인터페이스> <센서의 링크로컬 IPv6>`로 손실 0%, 1ms 미만 응답을 확인. 이후 IPv4 링크로컬(`169.254.x.x`)로도 접속됨.
- NetworkManager 프로파일이 `ipv4.method auto`(DHCP)였다. Ouster는 DHCP 서버가 아니라서 `Connection activation failed: IP configuration`이 났다. 이 링크는 링크로컬 방식이어야 한다.
- 전원: Go2를 켜야 Ouster가 동작하고 Orin2만 켜면 동작하지 않는다는 것이 실증으로 확인됐다(Go2 전원 레일에서 받음).
- 고정 IP 전환은 하지 않았다. 링크로컬 주소는 나중에 조용히 바뀔 수 있다는 경고가 계획서에 있다.

## 5. ouster_ros 빌드와 실행
- OpenCV 오류: `cmake`가 OpenCV 4.8.0을 찾는데 `.so` 파일이 없었다. 캐시를 지우고 다시 받아도 `libopencv-dev` 패키지 안에 라이브러리 본체가 없었다. 본체는 별도 패키지 `libopencv`에 있었고 의존성으로 자동 설치되지 않아서 따로 설치(`nvidia-opencv*`)했다. 시스템에 OpenCV가 세 벌 겹쳐 있는 상태로 정리는 보류했다. 이후 `Finished <<< ouster_ros [9min 26s]`.
- 실행 방식: 이 버전의 launch는 `sensor_hostname:=` 같은 인자를 받지 않고, YAML 파라미터 파일(`ros__parameters` 아래)만 받는다. 기본 `driver_params.yaml`을 복사해 `sensor_hostname` 한 줄만 바꾸는 방식이 안전하다. 센서 호스트명은 `os-<시리얼>.local`.
- 크래시: `os_driver`가 `exit code -6`(SIGABRT)으로 죽었고 launch 로그에는 원인이 안 남았다. `ros2 run`으로 직접 실행하고 lifecycle을 수동으로 `configure` → `activate` 전환해서 `activate` 단계에서 죽는 것을 확인했다. `configure`는 성공했고 센서 정보(OS-1-128-SR, 펌웨어 3.1.0, 모드 1024x10, UDP 프로파일 RNG19_RFL8_SIG16_NIR16)가 나왔다.
- 원인: 빌드한 `ouster_ros`(SDK 0.16.2)가 activate 때 `ChanField::WINDOW` 필드를 읽는데, 이 필드는 단일/이중 리턴 프로파일에서 펌웨어 3.2 이상부터 지원된다. 센서는 3.1.0이라 `std::out_of_range`가 잡히지 않아 `abort()`.
- 해결: 센서 펌웨어를 3.2.0으로 업데이트.
  1. 센서 메타데이터에서는 하드웨어 Rev를 찾을 수 없었고(`sensor_info`만 있음), Ouster 웹 다운로드 페이지에서 `Rev 07.1 v3.2.0`의 "Firmware Image"(.img)를 받았다(약 46MB). 올바른 Rev인지 사전 확인이 필요하다.
  2. 파일 이름에 공백과 괄호가 있어서(브라우저 중복 다운로드 `(1)`) `curl`이 실패. 이름을 `ouster_fw_v3.2.0.img`로 바꿔서 해결.
  3. 체크섬(`sha256sum`)이 공식 값과 일치함을 확인하고, dry-run이 `204 No Content`로 통과. 이어서 `curl -H 'Content-Type: application/octet-stream' --data-binary @파일`로 센서의 펌웨어 API에 업로드.
  4. `GET /api/v1/system/firmware`로 확인: `update_status: PENDING`, `commit_pending: true`가 나중에 `COMPLETE`, `commit_pending: false`, `v3.2.0`으로 바뀜.

## 6. 데이터가 안 보이던 문제 (QoS)
- RViz에 `PointCloud2`가 `Status: Ok`인데 `ros2 topic hz /ouster/points`는 아무것도 안 나왔다. 센서 토픽은 Best Effort로 발행되는데 `ros2 topic hz`와 Python의 `create_subscription(..., 10)` 기본값은 Reliable이라 구독이 연결되지 않는다.
- 해결: `--qos-reliability best_effort`(이 버전에서 `hz`는 지원 문법이 달라 확인 후 사용), Python은 `qos_profile_sensor_data` 또는 `ReliabilityPolicy.BEST_EFFORT`를 명시.
- 점군 내용: `x, y, z`가 `0, 0, 192, 127` 바이트 반복은 float32 NaN(`0x7FC00000`)으로, "해당 방향에 반환 없음" 표시다. `organized: true`라 128×1024 격자를 모두 채워 발행하고 반환이 없는 칸은 NaN, `is_dense: false`. RViz 렌더링이 느린 것(약 6fps)은 MobaXterm X11 포워딩 영향일 가능성이 지적됐다.
- 유효 점 비율: 1.5~4.7%. 거리 분포는 최소 0.68m, 최대 8.05m, 중앙값 1.22m로 실내 환경과 맞았고, 센서 설정(`operating_mode: NORMAL`, 방위각 0~360°, `min_range_threshold_cm: 50`)은 정상이었다. Claude는 OS-1-128-SR의 단거리 특성과 저반사율 표면 탓일 가능성이 높다고 추정했지만 검증되지 않아서 열린 이슈로 남겼다. 벽 정면을 향하게 해서 다시 재 보라는 제안이 있었고, 대화 문맥상 4.7%는 그렇게 재 본 값으로 보인다(정확한 측정 조건은 원문에서 확정되지 않음).
