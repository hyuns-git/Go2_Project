# 08. Orin NX에 유선을 연결하면 Wi-Fi가 불안정해지는 문제와 확장독 구조

## 한 줄 요약
Orin NX(Orin2)에 USB 이더넷과 PCI 이더넷을 연결하면 Wi-Fi가 잘 안 잡히는 문제를 추적하다가, 가설 몇 개가 틀렸음을 확인하고, 중복된 NetworkManager 프로필을 정리하고, 확장독의 포트 구조를 확정했다. 마지막에는 Orin2의 Ubuntu 22.04 재설치로 설정이 사라져 재설정 체크리스트를 요청하며 끝났다.

## 증상
Orin NX에 USB 이더넷과 PCI 이더넷이 모두 연결돼 있을 때 Wi-Fi가 잘 안 잡히고, 둘 다 뽑으면 Wi-Fi가 잘 된다.

## 기각된 가설 (증거로 틀렸다고 확인한 것)
| 가설 | 확인 방법 | 결과 |
|---|---|---|
| 기본 경로(default route) 메트릭 충돌 | `ip route` | 유선과 무선 모두 연결된 상태에서도 `default via <공유기> dev wlan0 metric 600`으로 정상. 기각 |
| USB 버스 대역폭 또는 전력 경합 | `lsusb -t` 구조 확인 | 근거 약함. 기각 |
| `rp_filter` 문제 | `sysctl net.ipv4.conf.*.rp_filter` | 해당 없음. 기각 |

원인이라고 정리된 것은 아래 "실제로 발견된 문제"뿐이고, 증상 전체가 이것 때문이었는지는 세션에서 확정되지 않았다.

## 실제로 발견된 문제
1. 같은 MAC과 같은 인터페이스(`eth1`)를 가리키는 NetworkManager 프로필이 두 개 있었다. 둘 다 `autoconnect=yes`, `ipv4.method=auto`(DHCP)라서, 로봇 내부망(`192.168.123.x`)에는 DHCP 서버가 없으니 계속 시도, 실패, 해제를 반복했다. 중복 프로필 삭제와 정적 IP(`192.168.123.20/24`) 적용으로 `eth1`이 안정화됐다.
2. 정적 IP를 줄 때 게이트웨이까지 넣어서 `default via 192.168.123.1 dev eth1`이 생기고 인터넷 경로를 가로챘다. `ipv4.never-default yes`로 막았다. 이 설정을 한 직후 `wlan0` 기본 경로가 잠시 사라졌다가 곧 돌아왔다(SSID가 5GHz용 SSID로 자동 전환되며 DHCP를 새로 받은 시간차로 Claude가 추정, 확정은 아님).
3. USB 이더넷 쪽의 `br0`(브리지)와 `br0-eth0`(브리지의 포트 프로필)가 있었다. 포트 프로필에는 IP 설정이 없어서 `ipv4` 설정을 넣으면 오류가 나고, IP와 `never-default`는 브리지 본체인 `br0`에 걸어야 한다. 반대편에 DHCP 서버가 없어서 `br0`은 계속 "IP 설정 가져오는 중"에 머물렀다.
4. `eth1`(로봇 내부망, `.20`)과 `br0`이 같은 `192.168.123.0/24` 대역에 서로 다른 IP로 떠 있었다. 메트릭 차이(102 대 425)로 당장 충돌은 없었지만 정리가 필요한 상태.

## 확장독과 배선 구조 정리
- 물리 연결: Go2 본체 → 확장독(Orin1, Orin Nano) → Orin NX(Orin2), 모두 랜선.
- 확장독에는 이더넷 포트가 앞뒤로 하나씩 총 2개이고, 앞은 Go2, 뒤는 Orin2에 연결돼 있다. 그런데 Orin1의 OS에는 `eth0` 하나만 보인다. 확장독 안에 2포트 이더넷 스위치가 있고 SoC는 그 뒤쪽의 내부 포트 하나에만 붙어 있기 때문으로 설명된다(추정). 실험적으로는 `eth0` 하나로 Go2(.161)와 Orin2(.20) 양쪽이 모두 응답했고, Go2 쪽 케이블을 뽑으면 Go2만 응답이 없었다.
- 그래서 Orin1에는 USB 이더넷 동글이 필요 없다. 한때 Claude가 "두 번째 포트가 없으니 동글을 Orin1에 꽂으라"고 안내했으나, 사용자가 이미 Orin2 랜포트와 도크 랜포트를 직접 연결했다고 정정해서 이 안내는 철회됐다.
- 한 가지 확인된 것: `tcpdump -i eth1`에서 반대편이 `169.254.x.x`(링크 로컬) 주소로 ARP, IGMP를 보내는 것이 보였고, `ssh -v`에서 원격 서버가 `dropbear`로 나왔다. Claude는 이것이 Orin1이 아니라 Go2 본체 쪽일 가능성이 높다고 추정했다. 이 추정은 최종 확정되지 않았다.
- Orin1에서 비밀번호를 재설정한 뒤 Orin2에서 `ssh unitree@192.168.123.18` 접속에 성공했다. 계정이 잠긴 것은 아니었고(`passwd -S`로 확인), 다른 주소로 접속해 있던 것이 혼란의 원인이었다.

## 이 세션에서 있었던 안내 오류
- 위의 동글 안내 외에도, `Wired connection 2` 설정 명령을 Orin1이 아니라 Orin2에서 실행하는 혼선이 있었다(프롬프트로 구분: `unitree@ubuntu`가 Orin1, `nvidia@nvidia-desktop`이 Orin2).
- 접속해 있는 장비가 어디인지 프롬프트를 먼저 확인하는 습관이 이 세션에서 여러 번 필요했다.

## 세션 종료 시 상태
- 해결: `eth1` 중복 프로필 삭제, 정적 IP 고정, 인터넷 기본 경로 보호
- 남음: `br0` 정리(자동연결 끄기 또는 별도 정적 IP), 증상 전체의 원인 확정
- 마지막 요청: Orin2를 Ubuntu 22.04로 다시 설치해서 설정이 사라졌으므로, 빠짐없이 다시 설정하는 프롬프트(07번 세션 후반과 같은 요청)

## 확인이 필요한 항목
- 확장독 내부 스위치 구조는 Unitree 문서로 확인되지 않은 추정이다.
- `169.254.x.x`로 신호를 보낸 장비의 정체(Go2 본체인지 Orin1인지).
