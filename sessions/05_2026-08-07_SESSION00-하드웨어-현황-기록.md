# 05. SESSION_00: 변경 없이 하드웨어와 배선 현황만 기록

## 한 줄 요약
이후 작업의 기준선을 잡으려고, 시스템을 바꾸지 않고 두 Jetson(Orin1, Orin2)의 사양, IP, 배선, 시계 오프셋을 측정해서 `STATE.md`에 적었다. 이 세션에서 "시계 오프셋은 상수"라는 기존 이해가 틀렸다는 것과 LiDAR 모델 표기 문제가 나왔다.

## 작업 방식 (이 프로젝트의 운영 규칙이 만들어진 지점)
- 세션마다 `SESSION_XX.md` 지시서를 주고, 범위 밖 작업은 제안하지 않는다. `STATE.md`에 없는 내용은 추측하지 않고 물어본다.
- 알게 된 사실은 `STATE.md`에 기록하고, 검증된 사실과 가설을 구분해서 적는다.
- 이 세션의 원칙은 "배선을 바꾸지 않고 확인만 한다".

## 측정한 하드웨어 현황
| 항목 | Orin1 (확장독) | Orin2 (외장) |
|---|---|---|
| 호스트명 / 계정 | `ubuntu` / `unitree` | `nvidia-desktop` / `nvidia` |
| OS | Ubuntu 20.04.5 LTS | Ubuntu 20.04.6 LTS |
| JetPack / L4T | R35.3.1 | R35.5.0 (JetPack 5.1.2 계열) |
| CPU / RAM | 6코어 / 7.2Gi | 4코어 / 15Gi |
| 이더넷 | 물리 RJ45 2개(육안), OS는 `eth0`만 인식(두 번째는 원인 미상, 이슈로 기록) | `eth0`, `eth1` 모두 링크 없음 (NO-CARRIER) |
| 로봇 내부망 | `eth0` 192.168.123.18/24, 1000Mb/s Full Duplex, 링크 정상 | 연결 없음 |
| 무선 | `wlan0` 일반 LAN 대역(192.168.1.x). 이 세션에서 Orin2에 쓰던 USB 무선 어댑터를 Orin1로 옮겨 연결했고 같은 주소를 받음 | `wlan0` 192.168.1.x (게이트웨이 192.168.1.1) |

의도한 구성: Orin2는 무선으로 인터넷을 쓰고, Orin1과 Orin2는 랜선으로 연결해 데이터만 주고받는다. Orin1에는 다른 네트워크 연결이 없다. 로봇 본체(192.168.123.161)에는 Orin1의 eth0(.18)을 통해서만 접근 가능하다.
(D115W 캐리어 보드가 언급되지만, Orin2의 정확한 SoC는 이 세션에서 `jetson_release`로 재확인하지 않고 잠정 기록만 했다.)

## Ouster LiDAR는 네트워크에서 보이지 않았다
- Orin1의 `eth0`와 `wlan0` 양쪽에서 `nmap -sn 192.168.123.0/24`, mDNS(`ping os-<시리얼>.local`), `avahi-browse`를 모두 시도했고 응답 없음. 잡힌 호스트는 자기 자신(.18)과 로봇 본체(.161)뿐.
- `os-<시리얼>.local` 조회가 공인 IP로 풀렸는데, 이것은 mDNS 응답이 아니라 일반 DNS로 넘어가서 공유기나 ISP가 없는 도메인을 안내 페이지 주소로 돌려준 것으로 판단했다. 그 주소로는 ping도 100% 손실.
- 블로그에서 본 "Ouster 기본 IP는 192.168.1.88"은 공식 기본값이 아니다. 여러 공식 자료와 사용자 매뉴얼(리눅스 연결 절차)상 고정 기본 IP는 없고, link-local 또는 DHCP로 주소를 받는다. 찾을 때는 `avahi-browse -lrt _roger._tcp`를 쓰라고 안내돼 있다. 호스트 쪽 인터페이스는 `nmcli`로 link-local로 설정해야 할 수 있다.
- 로봇 본체를 켜면 Ouster가 뜨거워지고 Orin2만 켰을 때는 그렇지 않다는 관찰에서, 전원은 로봇 본체 쪽에서 오는 것으로 추정했다. 이것은 가설이고, 케이블이 어디에 꽂혀 있는지는 이 세션에서 끝내 확인하지 못했다.
- 잠정 결론: 이 시점에는 Ouster가 어느 인터페이스에도 연결돼 있지 않은 것으로 기록.

## 시계 오프셋: 상수가 아니었다
- 이전 기록(01번 세션): 로봇 메인보드와 확장독 사이 오프셋 -49.13초를 "상수"로 정리했다.
- 이 세션: 로봇을 껐다 켠 뒤 `clock_offset.py`로 재측정하니 -92.0137초(범위 -92.0187 ~ -92.0089).
- 정정된 이해: 오프셋은 전원을 켤 때마다 달라진다. 로봇 메인보드에 백업 RTC가 없어서 부팅 시각에 따라 그 세션의 값이 정해지는 것으로 보인다(추정). 같은 세션 안에서는 변동이 0.01~0.045초로 안정적.
- 실무 의미: 오프셋 값을 설정 파일에 하드코딩하면 전원을 켤 때마다 깨진다. `scan_maker`는 원본 타임스탬프를 쓰지 않는 설계라 영향이 없다. 다른 스크립트에 -49.13초를 하드코딩한 곳이 없는지 확인하는 것이 숙제로 남았다.
- Orin2는 로봇과 연결이 없어서 오프셋을 측정하지 못했다.

## LiDAR 모델 표기
- 이 세션에서는 사용자가 한때 "L2가 확실하다(Unitree 공식 사이트 기준, FOV 360°×96°)"고 정정했고, 그에 따라 `STATE.md`에 L2로 반영됐다.
- 이후 사용자가 직접 재확인해서 **헤드 LiDAR는 L1이 맞다**고 확정했다(2026-11-04). 따라서 이 세션의 L2 기록과 FOV 값(360°×96°)은 틀린 값이고, 01번 세션과 이후 노드 이름(`scan_maker_l1` 등)의 L1 표기가 맞다.
- 가이드를 쓸 때 L1 사양은 Unitree 공식 문서에서 다시 확인해서 쓴다. 이 세션의 L2 수치는 쓰지 않는다.

## 백업
되돌아갈 지점으로 Orin1에서 아래를 만들고 크기를 확인했다.
```bash
cd ~/maps && tar czf ~/go2_backup_L1_$(date +%Y%m%d).tar.gz *.pgm *.yaml *.posegraph *.data waypoints.yaml
cp -r ~/ros2_ws/src/go2_nav_bridge ~/go2_bridge_backup_$(date +%Y%m%d)
cp ~/unitree_ros2/setup.sh ~/unitree_setup_backup_$(date +%Y%m%d).sh
```
결과: tar.gz 6.2MB(0바이트 아님), `setup.sh` 백업 374바이트.

## 세션 종료 시 상태
- 완료: Orin1, Orin2 사양, Ouster IP와 설정 확인(미연결로 결론), L1 스택 백업
- 일부: 배선도와 링크표(데이터는 모였고 정리만 남음), 시계 오프셋(로봇↔Orin1만)
- 건너뜀: 총 적재 중량 실측(사용자 판단으로 불필요)
- 범위 밖으로 미착수: 5개 층 실제 번호 정리, 계단 매핑 절차 문서화, 다음 세션 준비
