# 01. Go2 SLAM 지도 생성과 Point-to-Point 이동 첫 구현

## 한 줄 요약
Go2 EDU의 내장 L1 LiDAR로 2D 지도를 만들고 Nav2로 P2P 이동까지 가려고 했다. 표준 파이프라인(`pointcloud_to_laserscan` + `slam_toolbox`)이 안 돼서, 센서 데이터를 직접 재 보고 `scan_maker` 노드를 새로 만들었다. 이 세션에서 지도 생성은 통과했고 Nav2는 모든 노드가 active가 되는 데까지 갔다.

## 환경
- 로봇: Unitree Go2 EDU, 작업은 확장독의 Jetson Orin Nano (Ubuntu 20.04, JetPack 5, ROS 2 Foxy, CycloneDDS)에서 진행
- 접속: Windows 노트북의 MobaXterm (X11 forwarding 내장이라 RViz를 바로 띄울 수 있음)
- 패키지: 직접 만든 `go2_nav_bridge` (7월 30일에 만든 `cmd_vel_bridge`, `odom_tf_publisher`가 출발점)

## 진행 순서
1. 전날 만든 브리지 테스트: 로봇을 받쳐 놓고 `/cmd_vel`로 제자리 회전, 정상 동작. 같은 날 매핑(10단계)은 결과가 이상했음.
2. 왜 이상한지 측정부터 했다 (아래 "실측으로 확정한 것").
3. 측정값으로 `scan_maker.py` 작성, 빌드 후 `scan_only.launch.py`로 단독 검증 (게이트 1).
4. 제자리 한 바퀴 회전으로 벽이 한 겹 직선으로 나오는지 확인 (게이트 1 통과).
5. 시험 매핑을 두 번 비교하고 `test02` 맵 저장 (게이트 2 통과).
6. 그 맵으로 Nav2 기동. lifecycle 노드가 줄줄이 멈춰서 하나씩 원인을 찾음.
7. 초기 위치를 주고 `map → odom` TF가 살아나 모든 노드가 active가 된 데까지 확인.
8. 과정을 GitHub 저장소(`go2-nav`)에 문서화하고 다음 세션용 프롬프트 작성.

## 실측으로 확정한 것
| 항목 | 값 | 의미 |

| 점군 프레임의 좌표계 | `/utlidar/cloud_deskewed`의 frame_id가 이미 `odom` | base_link로 변환할 필요가 없고, 시계 문제도 피할 수 있음 |
| 더미 점 | 전체 138,668점 중 정확히 (0,0,0)인 점이 86.5%, 유효 점은 프레임당 약 1,556개 | `isfinite()` 검사를 통과해 버려서 scan 앞에 벽이 있는 것처럼 보임 |

| 각도 커버리지 | 예측 53%, 실측 93/180빔 = 51.7% | 파이프라인이 설계대로 동작한다는 확인 |

설계 결론: TF 조회를 아예 없앴다. `scan_maker`가 `/scan`과 TF를 같은 로컬 타임스탬프로 같이 내보낸다. 보행 중 몸이 앞뒤로 기울어도 scan이 오염되지 않게 `base_footprint`(yaw만 따르고 z=0)를 기준 프레임으로 쓴다.

## 지도 품질: 어떻게 돌았느냐가 결과를 갈랐다
- 방 한가운데에서 20 m 원으로 돌았을 때: 벽이 점으로 흩어짐. 유효 점의 수평 거리 중앙값(p50)이 약 0.95 m라서, 라이다가 벽을 비스듬히 계속 스치기 때문.
- 벽에서 1.5~2 m 떨어져 직사각형 경로로 돌고 코너에서 멈췄을 때: 벽이 한 픽셀 두께의 연속선으로 나옴. 평가 스크립트의 벽 평균 이웃 수가 2.51 (2.0~2.6은 얇음, 3.0 이상은 이중벽 의심). 점유 6.42%, 크기 271×196.
- 코너에서는 도는 전과 후 모두 3초 멈추는 것이 좋다고 정리했다. 하나만 고른다면 도는 전.

## 막혔던 곳과 해결
| 증상 | 원인 | 해결 |
|---|---|---|
| `ros2 topic echo --field`, `--once` 오류 | Foxy에는 두 옵션이 없음 | `timeout 3 ros2 topic echo ... \| head`로 대체 |
| 새 터미널에서 `Package 'go2_nav_bridge' not found` | `colcon build`만 하고 source를 안 함 | `~/.bashrc`에 `source ~/unitree_ros2/setup.sh`와 `source ~/ros2_ws/install/setup.bash` 추가 (이미 열려 있던 터미널에는 따로 source 필요) |
| 맵이 두 가지 모양으로 계속 번갈아 나옴 | 이전 slam_toolbox가 살아 있어서 두 인스턴스가 `/map`에 발행 | 이전 노드를 모두 종료 |
| Nav2 기동 후 `map_server`가 `unconfigured`에서 멈춤 | `map_saver`가 yaml에 쓴 `mode: trinary` 줄을 Foxy `map_server`가 못 읽음 | `sed -i '/^mode:/d' 맵.yaml` (저장할 때마다 반복됨) |
| `ros2 lifecycle get`이 끝나지 않음 | 응답 없는 노드를 만나면 무한 대기 | 항상 `timeout 3`을 붙임 |
| `planner_server`가 무응답처럼 보임 | AMCL은 `/initialpose`를 받기 전까지 `map → odom` TF를 내지 않음. 이때 `map` 프레임이 없어서 costmap이 못 올라옴 | 초기 위치를 명령으로 한 번 주면 해결. 정상 동작이었음 |
| `map_saver_cli`가 `Failed to save the map: timeout` | `/map`을 내는 노드(slam_toolbox)를 이미 종료한 상태 | 저장은 매핑 중에만 가능 |
| Nav2 재시작 후 다시 `unconfigured` | `map:=` 인자 없이 launch해서 없는 파일(`office.yaml`)을 찾음 | `map:=/절대경로/맵.yaml`을 항상 지정 |
| git push 인증 실패, 이어서 `rejected (fetch first)` | 비밀번호 인증 미지원, 그리고 저장소 생성 때 README가 이미 있었음 | 토큰으로 인증, pull 후 push |

## 설정값과 이유 (Nav2, `nav2_go2.yaml`)
- 프레임: 전부 `base_link` → `base_footprint`
- `allow_unknown: true`: false면 미지 영역(회색, 205)을 지나는 경로를 아예 만들지 않아 계획 자체가 실패
- AMCL: `min_particles 800`, `max_particles 3000`, `alpha1~4 = 0.2 → 0.30` (4족 로봇은 오도메트리 노이즈가 바퀴 로봇보다 큼)
- 속도: `max_vel_x`와 `max_speed_xy`를 같이 0.30으로 (실제 상한은 `max_speed_xy`), `max_vel_theta 0.50`, `acc_lim_x 2.5 → 1.0`, `acc_lim_theta 3.2 → 1.2`
- footprint: [0.45, 0.25] 사각형(0.90×0.50 m). Go2 실제 크기(0.70×0.31 m)보다 사방 10 cm 여유
- `cmd_vel_bridge`: `min_vx 0.10`, `min_vyaw 0.18` 부스트. Nav2가 목표 근처에서 0.02~0.05 m/s를 내는데 Go2 sport mode는 그 속도에서는 발을 떼지 않음

## 개념 정리
- 책상 밑 같은 곳에 로봇이 못 들어가게 하려면: Foxy에는 Keepout Filter가 없어서 맵 이미지(pgm)에 직접 벽을 그리는 것이 유일한 방법
- 다층 건물이라고 3D 맵이 필요한 것은 아님. 층별 독립 2D 맵을 두고 층 전환 때 `map_server`의 맵을 교체하는 것이 상용 서비스 로봇의 일반적인 방식. 계단 주행은 Nav2 밖에서 Sport API로 따로 다룸
